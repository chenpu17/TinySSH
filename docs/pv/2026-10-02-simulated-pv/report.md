# 模拟用户产品验证轮（Simulated PV）—— 2026-10-02

> 性质：**预演轮**。validation-plan §6 的产品验证 gate 唯一权威仍是**真人**参与者（复述准确、一周真实回用维度本质上需要真人真时间）；本轮用 6 个 subagent 人格在同一协议下完整走一遍，产出三样东西：①协议与工具链可执行的实证；②一份经伪影甄别的发现清单；③一份按预登记口径计算的 gate 矩阵（辅助参照）。**不能据此宣布 gate 通过。**

## 1. 设计

| 维度 | 实现 |

## 2. Gate 矩阵（N=6，pv_analyze.py 实算）

```
N=6  ⌈0.6N⌉=4  N/2=3  ⌈0.4N⌉=3
① 完成全部任务且总体偏好原型 : 0/6  (需 ≥ 4)  ✗   任务完成 6/6 但严格「偏好原型」仅 1/6（P04），其余 5 人「看情况」
② 复述准确                   : 5/6  (需 > 3)  ✓   （P04 依据静态简报复述不准确——demo 伪影所致，见 §3）
③ 一周回用（模拟意图）        : 6/6  (需 ≥ 3)  ✓
④ 新任务自发使用交接闭环      : 6    (需 ≥ 2)  ✓   S3 全部真实操作了接管/交还，且场景各异（政策亲读/批量抽查/危险命令手闸/破坏性动作前核对）
⑤ 上下文搬运 S1 vs S2/S3     : 13 vs 0*  （*S2/S3 搬运未单独编码）
⑦ 反模式信号                 : 全批×0、抱怨打断×1（P02 轻度）、回避交接×0
→ 出口建议（脚本）：调整交互再测（反模式优先否决；且偏好判据未达）
```

**对出口的解读**：核心假设信号为正——交接闭环在自由任务中被 6/6 自发采用且用法各异（validation-plan 最想验证的「新任务中自发使用」在模拟中成立）；「看情况」的 5 人全部给出一致的条件偏好（批量/留痕/委派类任务用原型，一次性小操作留 ssh），条件集中在「留痕可信度」（§3 第一组）。出口建议与真人 PV 的预登记判定无关，仅作二轮改进清单的输入。

## 3. 发现甄别（核心价值；对照 demo.ts / core-session / App.tsx 逐条核实）

### 3.1 真产品问题（真实 app 会复现）

| # | 级 | 发现 | 提出者 | 证据 |
|---|---|---|---|---|
| R1 | P2 | **「编辑后批准」的实际放行命令无处核对**：UI 有编辑对话框且 `edited` 参数真实传后端（App.tsx:1251,1851），core 审计 payload 里也带 decision Debug 串，但操作记录行不渲染 payload、卡片只标「（编辑后）」——追责用户无法一眼核对批了什么 | P01/P03/P05（3/6 独立命中，P05 称其为高危场景复用的决定性条件） | 源码核实 |
| R2 | P2 | **操作记录行无主机/会话维度**：审计 DB 有 session_id，UI 只渲染动作+命令（App.tsx:1925-1932）——多主机复盘「哪台机器上发生」需出工具 | P05（10 台机器的管理者第一诉求） | 源码核实 |
| R3 | P2 | **「接管」与「接管并停止任务」双按钮语义无解释**（3 人独立提出：P01 不敢点、P03 要猜、P06 只能猜） | P01/P03/P06 | UI 现状 |
| R4 | P3 | **取消 2FA 认证的报错被映射为「用户名或密码/密钥不正确」**：AuthFailed 一律走同一文案（App.tsx:157），取消应答也报凭据错误，把用户引向改密码 | P06 | 源码核实 |
| R5 | P3 | 主机表单 placeholder 是示例文案（"我的服务器/192.168.1.10"）而非字段名，首填按占位符语义定位失败触发校验 | P01 | UI 现状 |
| R6 | P3 | ⌘F 搜索无可见入口（需终端焦点才出现），自由探索时无任何反馈 | P01/P04 | UI 现状 |
| R7 | P3 | 现场简报右下关键提示（重确认范围/控制权历史）被截断不可读 | P04 | 截图确认 |
| R8 | P3 | 点击主机卡名称进入编辑而「连接」是按钮——高频动作（连接）低于低频动作（编辑）的可达性 | P02 | UI 现状 |
| R9 | 设计 | **人类→Agent 的任务委托入口缺失**（审批流只能被动响应 Agent 发起）：4/6 独立提出「协作编排只有一半」——V0 边界内（agent 经自家 chat/MCP 接任务），但 PV 信号一致指向 V1 应补「给 Agent 留目标/交接留言」 | P02/P03/P04/P06 | PRD 边界 |

另两条**设计语义**候选（非缺陷）：① 人类在「控制权：Agent」下打字不翻 chip/不打断 Agent——共享终端设计使然且真实 app 已审计（T12），但需要一个「打字时提示可接管/已留痕」的轻反馈；② 新会话默认控制权显示 Agent（产品前提是 Agent 常驻），对未委派的人生不安——需要首连引导语。

### 3.3 逐人一句话

- **P01 谨慎运维**：S1 1.5 分钟定位等号空格 crash-loop（真实 curl 200）；两次完整交接闭环、无盲批；偏好「看情况（批量/留痕类用原型）」。
- **P02 效率后端**：三态审批 5 秒差异化决策；S3 在批量归档后自发「接管抽查→交还收尾」；轻度抱怨打断；条件偏好明确。
- **P03 中间派全栈**：拒 docker prune、rm-rf 卡编辑后批准（加 test -d 守卫）；抓到留痕两处疑点（其一经实证为误读）；「前提：修复留痕缺陷」。
- **P04 焦虑新手**：零教学卡壳；分段审批与「重确认（受限）」兜底获好评；**唯一明确偏好原型**；S1 真实修复备份故障（4 次搬运）。
- **P05 委派负责人**：以追责视角专项检查操作记录；「决策步留人类、执行步走审批流」的自发编排；把留痕缺陷列为高危场景复用的先决条件。
- **P06 碎片化独立开发**：以「被打断 10 分钟回来」场景检验——简报停滞+无交接留言使恢复现场落空（伪影为主，指向 R9 交接留言）；发现 2FA 取消文案陷阱（R4）。

## 4. 对真人 PV 的输入（二轮前建议完成）

## 5. 诚实边界

- 6 名参与者是 LLM 人格：S1 的真实修复能力高于普通用户（基线时间不可比）；偏好/回用/复述是**模拟值**，无真实效度。
- S2/S3 的「任务完成」为流程口径（demo 无法真修故障）；故障任务的真实可达性由 T25 沙箱实测（五故障五解）与 §4 e2e 旅程（MCP+审批全链）分别覆盖。
- 反模式信号只有 6 个观察点，灵敏度远低于真人批次。
