# PV 主持手册与会话工具包（Session Kit）

> 版本：v1.0 · 日期：2026-09-30 · 上游：[validation-plan.md](../validation-plan.md)（**gate 唯一权威仍是其 §6**，本手册只是执行工具）
> 配套：[pv_env.sh](../../scripts/pv_env.sh)（沙箱与故障模板）· [dist.sh](../../scripts/dist.sh)（分发构建）· [pv_analyze.py](../../scripts/pv_analyze.py)（数据与分析）
> 读者：每场 90 分钟访谈的主持人。招募、预登记、执行、回收一次讲完。

## 0. 一图流

```
开测前 ── 招募 6–8 人 → 锁定 N → 预登记 gate 阈值（§2，git 提交即预登记）
        └─ 沙箱演练一遍全部任务（pv_env.sh reset → solve 核对）
每场前 ── pv_env.sh reset → 分发原型（dist.sh 产物）→ 参与者 Agent 接入 MCP
90 分钟 ── S1 基线(现有方式) → S2 引导(原型，含计划内接管→交还) → S3 自由(原型，只给目标)
当场后 ── 回收：audit.db 拷贝 + 录屏 + 画像卡 + 问卷 + 三段即时记录
一周后 ── 回访问卷（区分「没遇到适用任务」与「遇到但选择不用」）
全收完 ── pv_analyze.py 汇总 → 对照预登记阈值 → 决策评审（validation-plan §6）
```

## 3. 知情同意要点（开场口头 + 书面一页）

1. 全程录屏 + 出声思维，数据仅用于本研究（validation-plan §3 伦理条款）。
2. **全程使用我们预置故障的隔离测试机（127.0.0.1 沙箱容器），绝不接触你的生产机**；你的 Agent 只会被授权操作沙箱主机。
3. 原型会在远端 shell 注入提示符集成（OSC 133），逐主机显式确认、记录审计、可一键卸载——访谈内如出现该确认窗，属预期。
4. 可随时暂停/中止，不影响酬谢。

## 4. 每场前的环境准备（主持人清单，约 15 分钟）

```bash
# ① 沙箱：重建并注入全部故障模板，输出三行 ✓ 才算就位
scripts/pv_env.sh reset

# ② 原型：用 dist.sh 产物（版本号 = commit，记录到会话记录表）
#    参与者机器：挂载 dmg → 拖入 Applications → 首次打开右键「打开」过 Gatekeeper
#    （或 xattr -cr /Applications/TinySSH.app）

# ③ Agent 接入（参与者自己的 Claude Code / OpenCode）：
#    终端 a：tinyssh serve              # MCP HTTP 端点，默认 http://127.0.0.1:8722/mcp
#    终端 a（或界面 AGENT 区）：tinyssh agent create pv-p01 "PV参与者01"   # Token 只显示一次
#    把 MCP URL + Bearer Token 配进参与者的 Claude Code（或 stdio shim：
#    TINYSSH_TOKEN=<token> TINYSSH_MCP_URL=http://127.0.0.1:8722/mcp tinyssh-mcp）
#    自检：Agent 发一条「查看 /srv 目录列表」→ 审批卡出现 → 批准 → 终端有输出

# ④ 录屏开始（命名 P01-YYYYMMDD-S1.mp4，逐段一个文件更利于编码）
```

注意：每位参与者开始前必须 `pv_env.sh reset`——故障模板是确定性的，reset 后用 `check all` 复核。

> 两工具覆盖**等价**任务；条件顺序按招募序交替（奇数位 S1→S2→S3，偶数位 S2→S3→S1）抵消学习效应；全程出声思维。

| 时间 | 段 | 做什么 | 主持要点 |
|---|---|---|---|

## 6. S2 教学脚本（B′ 内嵌计划内「接管→交还」= V0 验收场景复演）

B′ 做到「定位到备份脚本失败」后，主持人引导：

1. **派发**：让参与者在自己的 Claude Code 里对 Agent 说「按 README 规范修复备份并验证」。Agent 发起 exec → **审批卡出现**——此处暂停讲卡片三态：批准 / 拒绝 / 编辑后批准；目标行显示会话与主机。
2. **接管**：在 Agent 待批或执行中，主持人口述「假设你现在想自己改——点会话卡上的**接管**」。终端解冻、Agent 冻结。
3. **人工处理**：参与者自己在终端修好配置（预期 2–3 分钟）。
4. **交还**：点**交还**。预期演示点：**Agent 旧的待审批请求随之失效（卡片作废）**；Agent 重新核实现场后**重新提交**新请求——这正是我们要验证的核心语义。
5. 观察记录：参与者是否理解「谁在控制」的界面信号；交还后 Agent 续接是否基于最新证据（validation-plan §5 介入有效性）。

S2 是教学段：卡壳就教，不作为能力评价。A′ 正常完成即可，用于观察原型基本操作的学习成本。

## 7. 任务卡（打印裁开；C 卡只有目标句）

> 等价性说明：A/A′、B/B′ 故障同构不同例（A=配置格式错误致 crash-loop，A′=配置值尾随空格；B=目标目录不符合规范，B′=源目录已下线），S1/S2 间不可凭记忆秒解。参考路径仅主持人可见：`scripts/pv_env.sh solve A|A2|B|B2|C`。

**任务卡 A / A′**（S1 用 A + 现有方式；S2 用 A′ + 原型）
> 这台服务器上的 webapp 处于崩溃循环。请定位原因并修复，使 `curl localhost:8080` 返回正常页面。沙箱内可随意折腾，不用怕弄坏。

**任务卡 B / B′**
> 这台服务器的定时备份不符合运维规范。请定位原因并修复，使备份按规范产出归档文件。验证标准：`/srv/backup/archive/` 出现新的 tar 包且日志无失败记录。

**任务卡 C（S3 自由段，只念目标句）**
> `/srv/dbapp` 的报表生成失败了，另外有一批记录的归档积压着。请把系统恢复到：报表能出数、积压记录按归档政策处理完毕。政策文件在服务器上。
>
> （主持人备注，勿念：归档政策含人工判断项——VIP 记录不可归档、近期记录不可归档；`migrate.sh` 是交互式确认，天然适合人工处理。观察参与者是否自发把判断类步骤留给自己/交给 Agent。）

**成功判据**（编码用）：A/A′=8080 返回页面；B/B′=archive 新包+日志无 FAILED；C=report.sh 退出 0 且 archive.csv 与政策一致（r002/r006/r012 归档，r004/r008 保留）。

- 这一周你是否又用了原型？是 / 否
- 若是：用在什么任务上？是否用了交接/接管？__

## 10. 分析与决策评审

全部场次回收后：

```bash
python3 scripts/pv_analyze.py --n <锁定的N> --data-dir pv-data/ --verbose
```

脚本输出每人与汇总的系统日志指标（审批次数/延迟、接管/交还次数、S3 窗口内自发交接信号、打断次数）、对照预登记阈值的 gate 判据矩阵、以及反模式信号优先的出口建议（**辅助计算；最终判定归 validation-plan §6，由决策评审会做出**）。审计哈希链可用 `--verify-chain` 校验，保证回收数据未被事后改动。
