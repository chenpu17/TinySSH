# 产品验证（PV）计划 — TinySSH

> 版本：v0.2 · 日期：2026-09-27 · 上游：[PRD](prd.md) §13
> 定位：**技术 Spike 验证架构可行性，本计划验证产品假设。两者并行（V0），PV 是进入 V1 的前置 gate。**
> 核心假设：把远程现场交给 Agent、随时介入、再拿回来，显著优于现有方式（复制粘贴 + 口头解释 + 各自为政）。

---

## 1. 决策问题

两个递进的问题：

1. **会不会用**：用户能否理解并完成交接闭环？（引导段回答）
2. **愿不愿意用**：在没有要求的情况下，用户是否会**主动选择**它？（自由段回答——产品假设成立与否取决于此）

不是验证：终端好不好用、功能全不全、演示是否惊艳。

## 2. 参与者（计划招募 8 人，最少 6 人开测；N 在开测前锁定并预登记 gate 阈值）

- **纳入**：已使用 Claude Code / OpenCode ≥ 1 个月；每周 ≥ 2 次维护 2–10 台 Linux 服务器；自述愿意在关键操作时介入
- **排除**：纯本地开发无远程场景；从未用过编码 Agent；需要团队审批流程的 SRE（后续画像）
- 渠道：个人网络 + 开发者社区招募；给予酬谢
- 记录：每人一份画像卡（工具链、服务器数量、当前远程操作方式、每周时长）

## 3. 原型（V0 thin slice）范围

**只做验证交接闭环所需的最小面**：

| 有 | 明确没有 |
|---|---|
| macOS 客户端；SSH → Linux（bash/zsh） | Windows/Linux 桌面端 |
| 导入 `~/.ssh/config` 与密钥 | 完整主机资产管理（分组/标签/跳板） |
| 一个共享会话标签页（持久 shell，cwd/env 延续） | 多标签广度打磨、主题/搜索 |
| exec（shell 模式）+ 授权卡片（批准/拒绝/编辑） | 端口转发、双栏 SFTP、多机编排 |
| 允许清单 + TTL 授权窗口（最小实现） | 复杂命令块 UI、块级交互 |
| 接管/交还（冻结 + 尽力停止 + 现场简报，旧队列作废） | 回滚（明确不承诺）、交还推送通知（V0 由用户回 Agent 对话发继续） |
| 操作记录时间线（人类可读） | 审计规模优化 |

**V0 首个可运行验收场景**（先于用户研究，验证核心价值「人拿回控制权后，人工处理真正受到尊重」）：

> 旧请求待审批 → 人接管修改现场 → 交还 → 旧请求（**含待审批卡片**）失效 → Agent 核实后重新提交。

**伦理与告知**：远端 shell 集成注入（OSC 133）须逐主机显式确认、落审计、可一键卸载；全程使用预置故障的隔离测试机，**不碰参与者的生产机**；录屏与访谈数据仅用于本研究并签署知情同意。

## 4. 任务设计（每人约 90 分钟，三段式）

> 两种工具（参与者现有方式 / 原型）覆盖**等价**的排障与配置任务；任务顺序在两种条件下保持一致以便对比，故障模板每次重置。

| 段 | 工具 | 内容 | 回答什么 |
|---|---|---|---|
| S1 · 基线 | 参与者现有方式（自己的终端 + Agent 工具链） | 任务 A（排查一次注入的服务异常）+ 任务 B（修改配置并验证恢复） | 对照基线 |
| S2 · 引导 | 原型 | 等价的 A′、B′；其中 **B′ 安排一次计划内「接管→交还」**（含一次交还后旧动作作废的演示） | 用户**能否**理解并完成交接（教学性质） |
| S3 · 自由 | 原型 | 任务 C（复合任务，如"排查并修复，其中一步较适合人工处理"），**只给目标，不要求、不提示交接** | 用户**是否主动选择**交接、用于哪一步、何时选择 |

- **顺序平衡**：条件顺序按招募序交替（奇数位 S1→S2→S3，偶数位 S2→S3→S1）以抵消学习效应；全程录屏 + 出声思维
- 每段结束 2 分钟即时记录（当前在做什么、为什么这样选）

## 5. 观察指标

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 上下文成本 | 复制粘贴 / 口头解释上下文的动作次数（S1 vs S2/S3） | 录屏编码 |
| 现场理解 | 事后能否准确复述「Agent 刚做了什么、被允许做什么」 | 复述编码（对照操作记录） |
| **自发采用（核心）** | S3 中是否主动使用交接/接管、用于哪一步、触发时机；不使用时的替代方式 | 录屏 + 系统日志 |
| 介入有效性 | 接管时机是否符合本人意图；交还后 Agent 是否基于最新证据正确续接（不重复已掌握信息、待核实对象先核实） | 录屏 + 系统日志 |
| 效率 | 任务完成时间；自评注意力投入（5 点量表 × 3 题） | 计时 + 问卷 |
| 反模式信号 | 持续全批、抱怨打断多、回避交接功能 | 录屏 + 访谈 |
| 留存 | 一周后是否主动再次使用；**区分「没遇到适用任务」与「遇到但选择不用」**（回访问卷附任务清单勾选） | 回访（微信/邮件） |

## 6. 决策 gate（三出口；阈值随 N 预登记）

| 结果 | 判据 | 动作 |
|---|---|---|
| **进入 V1** | ≥ ⌈0.6·N⌉ 完成全部任务且总体偏好原型；复述准确者 > N/2；一周回用 ≥ ⌈0.4·N⌉ 且其中 **≥ 2 人是在新任务中自发使用交接闭环** | 按 PRD §10 V1 范围推进 |
| **调整交互再测** | 出现反模式信号（全批 / 抱怨打断 / 回避交接），或自发使用率低但理解与完成度好 | 先修改授权与交接交互（授权卡片信息结构、TTL 默认值、简报呈现、交接唤起方式），二轮小样本复测 |
| **重新评估假设** | 多数参与者在 S3 自由任务中不采用交接闭环，且访谈显示非交互原因 | 暂缓完整客户端投入；评估转向「受控执行」轻定位或止损 |

**判据优先级**：**反模式信号优先于偏好判据**——即使完成与偏好达标，出现明显全批或打断抱怨，也先进入「调整交互再测」。（全批意味着授权交互失败，不是成功。）

## 7. 时间与并行

- 第 1–3 周：技术 Spike（[L0 §8](architecture/l0-system-design.md)）与 thin-slice 原型并行；同期招募参与者并锁定 N、预登记 gate 阈值
- 第 4–5 周：用户研究（每人 90 分钟 × 6–8 人）+ 编码分析
- 第 6 周：决策评审（对照 §6 gate），更新 PRD
