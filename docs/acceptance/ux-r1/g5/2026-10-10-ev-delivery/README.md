## 1. 结论

1. **`CGEventPostToPid`（ev2 原用路径）在本机对 tinyssh-app 静默失效**：**鼠标**在新旧
   两棵树、各 3/3 轮均然——guard 全过、调用返回成功、无任何报错，被测应用**零反应**。
   同一坐标改用 `CGEventPost(kCGHIDEventTap, ev)`（全局 HID）则生效。
   （**键盘不在本结论内**：本目录归档的机制级对照**只跑鼠标**；键盘仅有一次手工观察，
   见 §6，**不据此下结论**。）
2. **但全局 HID 正是 G0 签署 §4 明文禁止的机制**（`docs/ux/ux-r1-g0/g0-signoff.md:50`：
   「只用 ev2 PID 定向投递和逐事件守卫；**不得回退全局 HID 注入**」）。
   ⇒ 本机当前状态是：**签署授权的机制不可用，可用的机制未获授权。**
   **这是 R51/C2 的阻塞项**，须先取得**签署范围修订**（与「用本机」偏离一并登记），
   不得自行降级处理。
3. 因此 `ev2.py` 的修改取**保守**方向：**默认仍是签署授权的 `pid`**；`global` 为
   **fail-closed 开关**——未设 `TINYSSH_EV2_ALLOW_GLOBAL=1` 时 `--deliver global`
   在 guard 之前即 **exit 2 拒绝**，一个事件都不发。该环境变量是审计可见的授权凭据。
4. 即便获授权，global 仍带**三个静默失判陷阱**（§4：首次点击被吞 / 低概率丢事件 /
   焦点漂移），调用方**必须核验效果**，不得假设「投递即生效」。

## 2. 机制级对照（探针：`ev_delivery_probe.py`）

单变量对照：**坐标、应用、会话、时刻完全相同，唯一变量是投递目标**。

1. 启动被测应用，等 1280×800 窗口，置前。
2. 记录「哨兵区域」（左侧面板）基线像素 md5。
3. 每个 mode 前用全局点击把面板**复位到基线**，保证两者起点相同（若当前态已等于基线
   则不点击——故**并非每一轮** pid 点击前都有全局点击，见下「不是 key window」条）。
4. 以 `pid` / `global` 两种方式点击**同一哨兵点**（标定坐标 `(197,53)`），各记前后 md5。
5. 重复 3 轮，要求某 mode 三轮结论一致才采信。

> **两点口径（独立视觉复核提出，均为「措辞强于像素」）**：
> - 该哨兵点**不在截图区内**（`SENTINEL.y=53` < `REGION.y=105`），故 `＋` 按钮**从不
>   出现在任何 PNG 里**。本包的**像素**只证明「连续 global 点击与面板状态交替相关」，
>   **不独立证明**「被点的是 `＋` 按钮」——该因果依赖**从 `ev_delivery_probe.py` 沿用的
>   坐标标定**，本包内**无标定证据**。在 A/B 只作观测的框架下不影响结论，但**不主张**
>   「已证明 `＋` 是那个开关」。
> - 像素变化是**定宽面板内的视图切换**，不是面板「展开」：两态的分隔线 x **完全相同**
>   （最大列亮度跳变 31.0@x=423），仅 x∈[0,405] 的**内容**整体换屏——收起态是主机列表
>   （`全部主机`/`本机`+`密钥`），点击后是新增主机表单（地址/端口/用户名/认证方式/保存并
>   连接）。下文「展开/收起」一律指**这次视图切换**。

判定：`pid` 三轮全「无变化」且 `global` 三轮全「有变化」→ `pid_delivery_broken`。

### 结果（原始件：`main/`、`b1/`）

| 被测二进制 | sha256（前 16） | 轮次 | pid 变化 | global 变化 | 裁决 |
|---|---|---|---|---|---|
| 主树 `target/release/tinyssh-app` | `3bfecdf0d7934491` | 3/3 | **False ×3** | **True ×3** | `pid_delivery_broken` |
| B1 `.worktrees/old-ui/…`（tag `ea0b914`） | `2c3ab20dbc90db77` | 3/3 | **False ×3** | **True ×3** | `pid_delivery_broken` |

像素证据（`main/`）：基线与 `pid` 点击后 **md5 完全相同**（`4405d4771f…`），
`global` 点击后变为 `5d92b3e56697…`（切到新增主机表单）。三轮 md5 逐字相同，无抖动。
`b1/` 同理（`c8f7e62ccd…` → `919f431851…`）。

**不支持「本进程缺少注入权限（TCC/辅助功能）」这一解释**：全局 HID 投递本身就需要
「辅助功能」授权，而它在本机**成功**——故本进程**已获**该授权。（这是由「global 生效」
反推的授权状态，**未**直接查询 TCC 数据库；两者若不一致见 §6 未做项。）
`CGEventPostToPid` 返回成功却事件被静默丢弃，更指向该 API 路径自身，而非「没权限」。
**不是「窗口未成为 key」问题**：**至少一轮**（`m1`/`m2`）在 pid 点击**之前**有全局点击
（`ensure_baseline` 触发复位点击），其后 pid 点击窗口区域仍**逐像素不变**。（`m0` 因当前态
已等于基线而未触发复位点击——故此项由 `m1`/`m2` 支撑，非每轮。）

## 3. 工具级验证（`ev2_check.py`，原始件：`ev2-check/`）

机制级对照用的是探针**自建**的投递代码；本节验的是 **ev2 这个工具本体**（`--deliver`
接线、逐事件核验、guard 退出码），一律以 `subprocess` 调 `ev2.py`，不复制其代码。

**本节的产出分两层，切勿混读**（此为独立复核 blocking #3 的修正）：

- **接线段（`wiring`，C/D/E）——纯工具属性，构成本脚本的裁决**，恒应通过。
- **观测段（`observations`，A/B）——环境属性，只记录、不判定**。A/B 测的是「本机
  投递机制是否生效」，那是**环境**事实；把它写进裁决，环境一变（pid 恢复 / global
  失灵 / 并发干扰）就会产出「工具失败」的**假结论**（复核实测：并发干扰下 A 实例的
  应用被杀、窗口消失致像素「翻转」，被打成「pid 恢复了」）。

### 3.1 接线（裁决依据）

| 段 | 断言 | 结果 |
|---|---|---|
| C | 不存在的 pid → exit 2 且不投递 | **PASS**（`stderr` 含 `does not exist`） |
| D | 存在但非前台（`sleep` 子进程）→ exit 2 且不投递 | **PASS**（`stderr` 含 `frontmost`） |
| E | **不设** `TINYSSH_EV2_ALLOW_GLOBAL` 时 `--deliver global` → exit 2 且**一个事件都不发**（stdout 无 `T0=`） | **PASS**（`stderr` 含 `REFUSED`，stdout 空） |

- C/D 不打扰任何用户应用（`sleep` 无 UI；不存在的 pid 无副作用）。
- **E 是 fail-closed 闸门的直接证据**（此前完全未测，复核 blocking #3 建议补）：
  证明「未授权时 global 真被拦下」，而不只是「代码里写着拦」。E 段刻意用
  `ev2_noauth()`（不置该变量），因为其余段落的 `ev2()` 会自动置上它。
- 本轮 `verdict = ev2_wiring_verified`（C/D/E 全过）。

### 3.2 观测（环境属性，不进裁决）

| 段 | 观测项 | 本轮读数 |
|---|---|---|
| A | `--deliver global` 点击哨兵 → 面板状态**切换率** | **6/6 轮切换**（`flipped_rounds=6/6`）；9 次尝试（每轮 1–2 次），`unflipped_attempts=3`；rc 全 0 |
| B | **默认投递**（不传 `--deliver`，即 pid）→ 面板状态**切换率** | **0/6 轮切换**（`flipped_rounds=0/6`）；18 次尝试，`unflipped_attempts=18`；rc 全 0 |
| — | `observations.interference` | **空**（应用全程存活、无 rc≠0 尝试） |

- B 段**刻意不传 `--deliver`**：验的正是「默认值 = 签署授权的 pid」。
- **判断「是否切换」要看 `flipped_rounds`/`rounds_total`，不要看 `all_rounds_flipped`**
  （独立复核 F2）：后者问的是「是否**每轮**都切换」，6 轮里 5 轮切换会给 `False`，
  **低估**切换——恰把下面那条「环境变化检测」弄瞎。
- **B 的 `rc=0` 是关键证据**（独立复核 finding #3）：只看「没切换」无法区分「投了但
  没效果」（= 要证的环境事实）与「guard 拒绝、根本没投」（= 工具坏了却假过）。本轮
  18 次尝试 rc **全 0** ⇒ 事件**确实投了出去**，pid 路径对本应用**无效果**，而非被拒。
- `unflipped_attempts` 是**同一计数器、两段读法不同**（复核 F2）：A 段（global 本机有效）
  读作**丢事件**数——本轮 `3`（9 次尝试中 3 次没落地，见 §4②）；B 段（pid 本机无效）读作
  「每轮重试预算耗尽」——本轮 `18`，**不是**丢事件。JSON 内 `observations.field_notes`
  复述此约定。
- 该 JSON 自记 `bin_sha256 = 3bfecdf0d7934491…`（= 上表被测二进制），证据包自证身份；
  基线 md5 `4405d4771f…` 与 §2 机制级一致（坐标稳定，未受 §5 状态漂移影响）。
- **读法**：若见 `ev2_wiring_failed`，才是**工具**问题；若 `observations` 里 B 的
  `flipped_rounds` 不为 0（本机 pid 恢复可用），那是**环境变化**，须重估 `ev2.py` 默认
  投递与 G0 签署 §4 前提，而**不是**工具缺陷——本脚本不再把它写成裁决值。

## 4. 三个静默失判陷阱（①② 有归档读数；③ 为**未留档**的现场观察；均已写进 `ev2.py` / `ev2_check.py` docstring）

**① 激活后首次点击会被吞。** `activate()` 之后目标窗口尚未成为 key，第一个全局点击
被 macOS 吃掉用于「转 key」，表现为**像素不变**——与「投递失效」症状完全相同。
实测：静置 **2.5s** 后连续 **14 次**点击**全部落地**；静置约 1s 时首次点击被吞。
⇒ `ev2_check.py` 默认 `--settle 2.5`，并在测量前做一次**预热点击**（点完复位），
把转 key 的动作移出测量窗。

> **预热三张图的读法**（独立视觉复核提出）：硬不变量**只有** `00_baseline == 02_after_warmup`
> （预热后**必**回基线）；`01_warmup` 是**第一次**预热点击**之后**的状态——该点击落地则显示
> 展开态、被吞则等于基线。故 `01_warmup` 与基线**不等是正常的**（本轮即如此：首点落地→
> 展开→第二次点击复位），**不是**失败。上一版归档三图恰好全等，是「首点被吞」的巧合，
> **不是**不变量。

**② global 投递会低概率丢事件。** 实测：

| 仪表条件 | 丢事件 |
|---|---|
| 每次点击前后多张 `screencapture`（较重） | 约 1/6 |
| 每次点击仅一张截图、静置 0.75s（较轻） | **0/60** |
| `ev2_check.py` 工具级（含子进程启动） | `2/8`、`3/9`、`1/7`、`0/4`、`3/9` 次尝试（五次运行）——**仅 `2/8`（首版归档 JSON，git 可查）与本归档的 `3/9` 在仓库内可追溯**；`1/7` 为复核者复跑读数，`0/4` 与另一处 `3/9` **未留档** |

**丢因未定性**，已排除三项：
- **非事件间隔**：`move→down→up` 的 gap 取 0 / 60 / 150 ms，各 20 次，**全无丢失**。
- **非前台漂移**：丢失发生时 `frontmost` 仍等于目标 pid，`check_front` 未触发中止。
- **非「double-toggle 弹回」**：丢失的点击在 +0.12/+0.35/+0.8/+1.5s 四个采样点均停在
  原态，未观察到中间态。

⇒ **给调用方的结论**：用 global 做坐标取证时，**必须核验效果**（轮询状态/像素直到
变化），不得假设「投递即生效」；单次点击触发的计时端点会因丢事件产生**虚假长尾**。

**③ 焦点漂移/残留实例会让「全程 rc=2」伪装成工具缺陷。** 症状：guard 对**每次**调用
都返回 rc=2（什么都不投），但像素仍可能因**他窗口重绘**而「翻转」——于是 B 段假红，
被误报成工具缺陷（旧版会打成 `pid_delivery_now_works`/`ev2_delivery_failed`）。
**作者在开发过程中现场撞到过两次**（**未留档**——最终归档的 `ev2-check/app.err` 无 panic、
亦无相关日志，故此处只作**定性描述**，**不作**可复核主张；独立复核 F4 已指出此点）：

- 残留 `tinyssh-app` 实例占住库写锁 `/tmp/ev2_check/tinyssh.db.lock` → 新实例
  `panic` 退出 → 探针 20s 内取不到窗口（症状与「应用起不来」无异）；
- 焦点被其他窗口抢占 → 前置核验前全程 rc=2。

缓解（本轮已加入 `ev2_check.py`，均属**把环境问题与工具问题分开**）：
① 清掉陈旧的 `.lock` 锁文件；② 应用早退时**立即**打印 `app.err` 末尾而非白等 20s；
③ **测量前置断言「前台 = 被测应用」**，重试 6 次仍不成立即以 exit 2（**环境问题**）
退出，不继续产出垃圾数据；④ **结构性消除**（复核 blocking #3 的建议）：把 A/B 降级为
`observations`、裁决只由纯接线断言 C/D/E 决定——于是「环境干扰致像素翻转」**再也不会**
被写成工具裁决；另记 `observations.interference`（应用中途死亡 / 有 rc≠0 尝试）提示
观测不可信。⇒ 若见 `ev2_wiring_failed`，**先查前台与残留实例**，再怀疑工具。

## 5. 附带发现：webview localStorage 让原生 UI 布局跨轮漂移

dev 二进制把 UI 状态持久化在 `~/Library/WebKit/tinyssh-app/WebsiteData/LocalStorage/`
（**直接式**布局 `<bundle>/WebsiteData/LocalStorage`；多数 Tauri/WebKit 应用是
`<bundle>/WebsiteData/Default/<hash>/<hash>/LocalStorage` 嵌套式）。实测键
`ui.hostbar` / `ui.hostbar_w` / `ui.r15s1` / `ui.r15epoch` / `ui.r15step`。一次交互把
`ui.hostbar` 置 0（隐藏主机栏）后，**下一轮启动仍是该布局**——于是同一套坐标在两次运行
里指向不同控件，探针会以「两种投递都无变化」**静默失判**（本轮实测到：基线 md5 从
`4405d4771f…` 变成 `2a7b5e1ddf…`，区域全空）。

> **口径**：`2a7b5e1ddf…` 是当时**现场观察值**，其 PNG **未留档**（该次运行不属归档运行，
> 目录内无对应原始件）——故此处只作**定性说明**（「状态漂移确会改变基线」），
> **不主张**该具体 md5 可复现。可复现的是**成因**：`LocalStorage` 持久化 UI 布局。
>
> **键名口径（独立复核 #4 提出）**：`ui.hostbar` 等键名是当时**现场读取**所得；现该目录
> 已是**空目录**（0 文件），**第三方无法再就地复核键名清单**。故键名属**未留档的现场观察**，
> **不作**可复核主张。可复核的是**成因**：该 `LocalStorage` 目录确实存在且持久化 UI 布局
> （`--reset-ui-state` 的备份机制、以及 `main/`+`b1/` 基线 md5 随状态漂移而变，均为旁证）。

⇒ 探针加了 `--reset-ui-state`：启动前把匹配到的 `LocalStorage` 目录 **`mv`** 到
`<out>/ui-state-backup/`（可逆，不删）。**任何依赖坐标的原生取证都必须先复位该状态**，
否则「坐标漂移」会被误判成产品缺陷或投递失败。

**勘误（独立复核 finding #1，已修）**：本目录**首版**称该复位「生效」——**当时不成立**。
首版 `reset_ui_state()` 用 4 段 glob `*/WebsiteData/*/*/LocalStorage`，实测匹配 **0** 个
（两型真实布局都不匹配，见上）；即该开关**一直在静默空转**。归档 `main/run.log` 与
`b1/run.log` **首行**那句 `reset ui state: moved 0 LocalStorage dir(s)` 就是证据——
