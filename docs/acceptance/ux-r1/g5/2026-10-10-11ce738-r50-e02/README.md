# R50 / E02 —— 深浅外观 × 主要终端配色的对比度测量

日期：2026-10-10　HEAD：`11ce7389a26f96c22a8844bfad0b6090fe572a94`　证据目录：`2026-10-10-11ce738-r50-e02/`

## 1. 范围与判据

行级要求（交付文档 §E02）：**所有文本、选中、错误、弹窗对比度合格，无白底白字/极暗说明**；
取证方式「样式测量 + 视觉」。

- **本档覆盖**：样式测量（可自动化）。**视觉那一半**（人眼确认无白底白字）由本档的
  `screenshots/` 供人工复验，**本档不代替人眼下结论**。
- **判据取项目既有口径**：正文 **4.5:1**、大字 **3.0:1**（WCAG AA）。这不是本档新立的阈值——
  R40（`docs/acceptance/ux-r1/g4/2026-10-09-97035c8-r40/README.md:149`「低于 AA 4.5」）、
  R41、R42 均按此判，且 R40 已按此口径修过同源缺陷。大字定义：≥24px，或 ≥18.66px 且字重 ≥700。
- **被测对象**：`ui/src/styles.css` 的 CSS 变量与规则，经 dev server（`http://localhost:5183`）
  在 headless Chromium 中**实际渲染**后读取 computed style。
- **范围限定**：浏览器域 demo（`ui/src/demo.ts` 内存后端）。**不含**原生打包产物的窗口装饰、
  系统深浅跟随、以及 macOS 原生控件。
- **覆盖面边界（测了哪些面、没测哪些面）见 §5.7**——这一节是判据的一部分，不是附注。

## 2. 方法（探针 `probe-e02-contrast.cjs`）

| 段 | 测什么 | 怎么测 |
|---|---|---|
| **A** | 4 套终端配色 × 2 种应用外观的**前景/背景**，以及 16 个 ANSI 色与选中背景的对比度 | 逐套经设置面板真实切换；前景读 `.xterm-rows` 的 computed `color`，背景读 `.xterm-viewport` 的 computed `backgroundColor`，**并用截图像素做地面真值**；再与源码 `THEMES` 表逐字段对账 |
| **B** | 界面（chrome）**所有可见文本节点** | 遍历文本节点，用 effBg 沿祖先链**逐层 alpha 合成**求实际底色，算比值；按 4.5/3.0 判。终端子树（`.xterm`）排除，由 A 段单独负责 |
| **B′** | **placeholder**（属性文本，B 段的文本节点遍历**扫不到**） | 读 `::placeholder` 的 computed `color`，带 alpha 时与输入框底色合成后再算比值 |
| **C** | 选中 | 界面 `::selection` 规则（CSSOM）+ 真拖选后的像素；终端选中层 + 像素 |

**B/B′ 段的桶（14 个）**——按「用户此刻看的是哪一屏」划分，同一屏不重复计：

| 桶 | 何时 | 为什么必须单列 |

| `page` | 已连一个主机 | 主工作屏 |
| `hover` | 主机卡悬停 | `.host-card-side`（含连接钮）默认 `opacity:0`，只在悬停/聚焦时才画出来 |
| `settings` | 设置弹窗 | 独立浮层 |
| `addhost` | 添加主机表单 | placeholder 最密集的输入面 |
| `hostkey` | 首次连接指纹确认弹窗 | `.hk-dialog` |
| `banner` | 连接失败横幅 | 错误态文案 |
| `afterAll` | 收尾整页复扫 | **只用于自证无漏报**（见 §5.4），不参与「共测 N」的组数统计 |
| `ph-page` / `ph-settings` / `ph-addhost` | 上述三面的 placeholder | 同上 |

### 探针自身的四处踩坑（都会**静默给出假读数**，登记在此以免误信）

1. **终端背景不能用父链 walk 找**。xterm 把主题背景画在 `.xterm-viewport` 上，而它是
   `.xterm-screen` 的**兄弟**（绝对定位互相覆盖），**不在文本节点的祖先链上**。父链 walk 会
   一路走到应用底色，把深色终端读成浅色底 ⇒ **假的「白底白字」**。正确做法 = 直接读
   `.xterm-viewport` 的 computed backgroundColor。**本探针初版正是踩了这个坑**（读数
   `effBg=rgb(234,238,242)` 而像素真值是 `rgb(16,20,26)`）。
2. **可见性必须查祖先**。只看元素自身 `opacity` 会把「祖先 `opacity:0`」的元素当成可见——
   本 UI 的 `.host-card-side`（含连接钮）默认 `opacity: 0; pointer-events: none`
   （`styles.css:977` 开块、`:983` 置 0），显形有三条路径（`styles.css:986-988`）：
   `:hover`、**`:focus-within`**、以及 **`:has(.host-connect-btn:disabled)`**。初版据此报出
   `.host-connect-btn` 深色 3.78「不合格」，而那一刻它**根本没画出来**（像素全为页面底色）
   ⇒ 假红。改用 `checkVisibility({checkOpacity, checkVisibilityCSS, contentVisibilityAuto})`
   后该条从默认页消失，只在**悬停态**出现（那才是用户看得到它的时刻）。
3. **弹窗不一定有 `role=dialog`**。指纹确认弹窗是 `.hk-dialog`（无 role）；只用
   `[role=dialog]` 会**一条都抓不到**并静默返回空集。选择器改为 `.hk-dialog, [role=dialog]`。
4. **placeholder 不是文本节点**。`<input placeholder="…">` 的字样只存在于**属性**里，
   DOM 文本节点遍历**永远不会命中它**（本档初版因此漏掉全部 placeholder，其中包含
   添加主机表单的 5 个输入提示）。必须单独读 `::placeholder` 的 computed style。

> 上述四处均为**探针**缺陷，不是产品缺陷；修好后才形成下表读数。

### E02-3 的处置不能简化为「换 `--accent-text`」（本档实测）

`--accent-text`（`styles.css:22`）是 R41 为「panel3 提亮底上的 accent 正文」造的专用档，
但把它套到 E02-3 列出的四处，**只有一处修得好**：

| 位置 | 现用 `--accent` | 改用 `--accent-text` | 结论 |
|---|---|---|---|
| 深色 `.host-connect-btn`（底 `#263848`） | 3.78 | **4.41** | **仍不合格**（差 0.09） |
| 深色 `.ts-opt`（底 `#1f303f`） | 4.24 | **4.94** | 合格 ✅ |
| 浅色 `.host-connect-btn`（底 `#d4e1e6`） | 3.99 | **3.99**（浅色 `--accent-text` ≡ `--accent` = `#1f767c`） | **完全无效** |
| 浅色 `.ctl-badge.human`（底 `#dfe9ec`） | 4.32 | **4.32**（同上） | **完全无效** |

> 注：`--accent-text` 的声明值 5.07:1 是**相对 `--panel3` `#232d3d`** 算的；而
> `.host-connect-btn` 的实际底是 `--accent-soft` 与 `--panel3` **alpha 合成**后的 `#263848`
> ——比 `--panel3` 亮，所以同一个前景色到不了 5.07。**引用 5.07 来论证按钮合格是错的。**
> 浅色同理：`styles.css:21` 记的「浅色同 `--accent` 4.52:1」，其底在 `styles.css:83` 的
> 浅色 `--accent-text` 注释里写明是 **`--panel3` `#e8edf2`**（本档实测恰好 4.52）。换到按钮的
> `#d4e1e6` 上只剩 **3.99**。（注：`#eaeef2` 是**浅色 `--bg`**，不是 `--panel`——浅色
> `--panel` 是 `#f4f6f8`，在它上面 `--accent` 是 4.92；无论取哪个，结论都不变。）
>
> 浅色档没有独立的 `--accent-text`（`styles.css` 里浅色 `--accent-text` 直接等于
> `--accent`），故浅色的两处**必须另想办法**（加深 `--accent` 本体、或给这两处单独的深色档）。

**`ts-swatch` 的 4.13 不算 chrome 缺陷**：它是设置面板里的**配色预览小样**（`Aa`），
按设计就渲染**该配色自己的**前景/背景，因此它的比值必然等于该配色的正文比值——
Solarized 浅色那一格 4.13 正是 E02-1 的**忠实预览**，是**症状不是新缺陷**。
（它在**两种应用外观下都出现**，因为 swatch 只跟终端配色走。）

## 5. 口径与未做

1. **视觉那一半未做**：本档只出样式测量与截图，**不代替人眼下「无白底白字」的结论**。
   截图在 `screenshots/`（含两外观的**欢迎页**/默认页/悬停/设置/添加主机/指纹弹窗/失败横幅/
   终端选中）。
2. **ANSI 16 色是「按声明表算」而非「渲染出来量」**：demo 后端不产出带 ANSI 转义的输出，
   16 色在页面里无法渲染。**依据**是 §3.1 的对账——8 组实测前景/背景与声明表逐字段相等，
   故声明表即运行调色板。若审核者不认此论证，则应另造带 ANSI 输出的会话复测；**该分歧点如实登记**。
3. **只测浏览器域**：不含原生打包产物的窗口装饰/原生控件；也不含系统「跟随系统」深色下
   与系统主题的交互（本档是显式切「深色」「浅色」两档）。
4. **`afterAll` 桶用于自证无漏报**：收尾时对整页复扫一遍（81 节点/外观），其**不合格组与
   前述各桶的并集完全重合，无一组是新的**（`e02-summary.json` 中 `afterAll` 独有的失败组
   为空集）。⇒ 说明按屏分桶没有漏掉任何可见面。
5. **对比度按声明色算，不按抗锯齿后的像素算**——这是 WCAG 的标准做法（声明色是设计意图）；
   像素只用于**验证底色归属**（哪块像素属于哪个元素），不用于比值本身。
6. **大字档（3.0）在本数据集里只被 `.welcome-title` 行使**（19px / w700，深色 13.68、
   浅色 11.83，均合格）。`e02-summary.json.largeEverExercised` 字段如实记录。
7. **覆盖面边界（判据的一部分）**：
   - **已测**：欢迎页、主工作屏、主机卡悬停、设置弹窗、添加主机表单、指纹确认弹窗、
     连接失败横幅，以及其中的 placeholder。
   - **未测**（**不在本档「合格」主张的范围内**）：凭据管理弹窗、SFTP/文件面板、端口转发面板、
     协作面板、搜索/终端内搜索、Agent 委托弹窗、导入 `~/.ssh/config` 面板、标签列表弹窗、
     分屏态、窄窗态（那些是 E01/E03/E06 的面）。这些面里若也有 `--dim`/`--accent` 正文，
     **本档没有量过，不得据本档声称它们合格**。
   - **不在扫描范围内**：`<input>` 的**已输入值**（只测了 placeholder）、
     `title=`/`aria-label` 等**悬停提示**、canvas/SVG 内绘制出来的字。
   - 探针只判**元素自身可见性**（`opacity`/`display`/`visibility` 祖先链 + 尺寸 ≥1px），
     **不判遮挡**。故 `welcome` 桶里若有被欢迎页盖住的底层元素，仍会被计入（实际未发生：
     `welcome` 桶 81 节点全部来自欢迎页子树）。
8. **五处发现均未修复**（本档是验证任务，改产品代码不在范围内）。
9. **应用外观与终端配色相互独立**（`App.tsx:4297` 注释、`:1498` `data-chrome`）：A 段的 8 个
   组合里，终端前景/背景只随配色变、不随外观变——这是**设计如此**，不是缺陷。
10. **单次干净自证**：归档目录在正式跑之前被 `rm -rf` 清空（连 `.run-attempts` sidecar 一起
    删），故 `e02-raw.json.run.attempts === 1` 即证明目录里的每张 PNG / 每个读数都来自
    **同一次**运行，没有上一轮孤儿文件混入。同一字段还带 `probeSha256`（探针自身哈希，
    把读数钉死在那一版探针上）。
11. **可复算**：`e02-summary.json` 与 `e02-measurements.csv` 由 `summarize-e02.cjs` 从
    `e02-raw.json` 生成（判据、分桶、分组口径都写死在脚本里）——审核者跑一遍即可独立复现，
    不必采信本档口述。
12. 探针在 `docs/` 下，`playwright-core` 装在 `ui/` 下，故用 `require.resolve(..., {paths})`
    显式解析；不依赖调用者 cwd。运行前需 dev server（`npm run dev --prefix ui`）。
