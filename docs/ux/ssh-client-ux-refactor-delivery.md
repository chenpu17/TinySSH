## 1. 执行约定

- PM：范围与用户研究；UX：交互、视觉与原型；FE：React/Tauri 前端；Core：Rust/协议/存储；QA：独立验收。角色不限定人数。
- 每张任务卡包含设计条款、实际修改模块、契约增量、失败路径、迁移影响、验证证据。不能只写“完成页面”或以截图作为后端完成证明。
- 阶段状态使用 `待开始 / 实施中 / 待验收 / 通过 / 阻塞`；阻塞写清依赖和负责人，不写模糊百分比。
- G0 后由团队估算工作量与人员投入，再形成日期计划。本文不提供缺乏团队条件的工期承诺。
- “必须”项是本轮发布范围。延期必须修改范围与对应产品承诺，不允许上线一个只隐藏不可用按钮的半成品流程。
- C1–C10 是 R03 冻结的**契约编号**，不是“已实现”的证明。下面依赖列只用 R 任务或明确的阶段出口；真正需要已实现能力时按 R 依赖执行。各 C 的实现归属见 §2.1，禁止把“已评审 C1”误作“可以调用完成的 C1”。

### 1.1 开工结论与 G0 签署

文档可支持 G0 开工：确定实际负责人、制作原型、冻结契约、准备 fixture 和采集基线。三路静态审核通过只说明这个输入可用；不会自动勾选任何实施/运行验收项。

进入 G1 前必须实际提交并由 PM/UX、FE、Core、QA 共同记录：

1. R00 范围和全部旧功能去向；首版限制、后续能力与本轮行为变更清单。
2. R01/R02 可交互原型与组件样例，至少走完五条主要任务，覆盖 S01–S11 的关键失败/窄窗/键盘状态；三张静态图不代替它。
3. R03 的 C1–C10 正式 wire、错误码、合法状态转移和示例；包含提交未知、执行模式拒绝、停用 admission、连接取消竞态的可断言序列。
4. 迁移/协议 fixture 清单及兼容样例，尤其旧 Agent 配置与 Shell 缺能力的旧客户端错误路径；对应实现可在后续任务完成，测试预期必须先确定。
5. R04 环境、旧版原始样本、采样脚本及统计口径；对所有未决事项注明是否阻塞出口。关键语义问题未关不得签署 G0。

该记录需含版本/文件摘要、评审人角色、日期、通过/未通过与具体遗留；未分配人员或没有证据时状态为“待执行”，不是“默认通过”。

## 3. 功能验收矩阵

所有项默认必须通过。下表的“层级”指最低证据要求，不能用 demo 代替 native/core。每项可拆多个测试；保留失败注入和原始结果。

### A：连接与主机

| ID | 场景 | 必须观察到的结果 | 层级 |
|---|---|---|---|
| A01 | 新装无数据 | 只呈现清楚的连接/导入/本地终端入口，无 MCP 空卡；无自动远端连接 | 原生+视觉 |

| A04 | 密钥、密码、ssh-agent、两轮交互认证 | 真实 sshd 各成功一次，错误凭据各失败一次；提示不串 attempt | 真实 SSH |

## 4. 性能与稳定性门

以下为本轮**设计目标**，不是测得结果。基准环境建议 Apple Silicon、16GB 内存、release 构建；至少覆盖团队支持的最低 macOS 与当前主版本，G0 固定具体机型/系统。服务端为隔离 Linux sshd，网络 RTT 记录在报告。每项保留旧版与新版原始数据；首轮未达标先定位，变更目标须在重测前登记理由。

| ID | 指标与方法 | 发布门 |
|---|---|---|
| P1 | 启动到主机列表可操作，已有 20 主机；冷/热启动各 10 次分开统计 | 热启动 P95 ≤1.5s，冷启动 P95 ≤3s；无网络等待主机列表 |
| P2 | 同一 release 会话切换 100 次；输入到本地可见回显 100 次 | 切换 P95 ≤100ms；本地回显 P95 ≤50ms；远端单列 RTT，不把网络延迟算 UI 固有成本 |
| P3 | 普通新 SSH，无 shell 集成、已信任、无人工认证；同机同网络 30 次 | 不等待 shell marker；新版 P95 不高于同环境旧基线，且本地测试 sshd P95 ≤2s；阶段延迟可解释 |
| P4 | 100MB 上/下载各 5 次，同时终端输入/切换 | 文件摘要正确；终端切换 P95 ≤150ms；吞吐中位数 ≥旧基线 90%，未知进度不编百分比 |
| P5 | 一个会话 1k 行/s 输出、共 10 会话、持续 30 分钟；按下述预热/采样协议 | 不冻结/不掉输入；最终快照一致；停止并静置后内存较预热基线增长 ≤20% 且末段无持续上升趋势 |
| P6 | 100 次创建/关闭、200 次标签切换、50 次面板变化 | 每存活会话至多一个输出订阅；关闭后终端实例、监听器和活动执行引用清理，历史任务摘要可保留；无线性资源增长 |
| P7 | 10,000 目录条目，真实响应与 UI 渲染分别计时 | 数据到达后首屏可操作 ≤300ms；滚动无需渲染全部行；网络耗时独立报告 |

首次试验发现 OS 调度、WebView 指标采集或环境限制时，将该项记为未完成/环境阻塞并给复测环境；不可把“没测到”判为通过。吞吐/内存目标均需同时检查正确性，禁止丢真实状态换取性能数字。

**P5 固定测量协议**：R04 在采样前冻结终端 rows/cols、每行长度与内容、UTF-8 模式、scrollback/命令块/审计缓存上限、会话数量及输出脚本。预热时先让参与测试的缓存达到相同已配置容量（不能用空缓冲作基线），停止预热输出并静置 60 秒；随后每 5 秒采集一次、连续 60 秒的中位数作为基线 B。正式测试停止后同样静置 60 秒，再采 60 秒中位数 E，以 `(E-B)/B` 计算增长。

内存口径固定为同一个采样脚本记录的应用进程及其专属 WebContent/GPU 辅助进程 RSS 合计，同时分别保留进程曲线和 PID 归属；不混用 RSS 与 footprint，不把共享系统服务不明比例计入其中。R04 必须验证专属进程归属，无法可靠归属则该项未完成。最后 10 分钟按分钟取中位数，连续 10 点严格递增或该窗口净增长超过 5% 视为持续增长，需解释并复测；不以单个 GC 瞬间峰值判泄漏。新旧版本使用相同上限、数据和口径，不能通过降低新版本缓存容量规避门限。

## 5. 真人体验验证

### 5.1 样本与任务

招募 **6 位**目标用户：每周至少两次 SSH 工作，通常管理 2–20 台服务器；包含熟悉命令行及已有 GUI 客户端的用户。无需使用过 Agent。避免开发团队成员参与正式计分；模拟人格只用于预演。

使用隔离测试服务器，不要求参与者提供生产凭据。准备操作目标等价但主机/文件/答案不同的任务集 A/B。按招募前锁定编号分配：P01/P03/P05 先原工具后 TinySSH；P02/P04/P06 先 TinySSH 后原工具。P01/P04/P05 原工具用 A、TinySSH 用 B；P02/P03/P06 原工具用 B、TinySSH 用 A；两种工具的出场顺序各 3 人、各工具任务集 A/B 也各 3 人。分配完整记录，不把小样本称为完全消除学习效应。工具切换间不提供 TinySSH 操作演示，不安排必须喜欢新软件的引导；每位参与者只接触自己当轮任务所需信息。

| 任务 | 用户目标 | 观察内容 |
|---|---|---|
| U1 首次连接 | 导入或添加指定服务器并运行 `whoami` | 是否找到入口、理解认证、处理错误、确认连接目标 |
| U2 日常终端 | 查看日志、搜索指定错误、复制一段输出 | 焦点、搜索发现性、复制结果、终端习惯是否成立 |
| U3 多会话 | 连接另一台机器，执行不同命令，再回第一台 | 是否知道当前主机，有无误发命令、标签/分屏理解 |
| U4 文件往返 | 上传一个测试包、下载日志、处理同名文件 | 发现文件入口、明确源/目标、理解冲突与进度 |
| U5 断线恢复 | 在人为中断网络后恢复工作并退出 | 能否分辨旧画面与新连接、找重连、理解退出影响 |

“无指导完成”指主持人仅给任务目标和必要测试环境信息；任何告诉参与者点击哪里或解释产品状态的帮助均记为一次求助，并使该次任务不计独立完成。操作失败可自行恢复，仍记录耗时和误操作。

### 5.2 客户端发布门（唯一数值来源）

- **任务完成**：U1–U5 每项至少 5/6 独立完成；不能用全体总平均掩盖文件或断线任务难用。
- **初次上手**：U1 从已有合法凭据的任务开始到可输入命令，中位数 ≤3 分钟；预置的失败修复作为单独子任务计时，不混算网络等待。
- **关键误操作**：0 次由 UI 目标含糊导致的误主机执行、误目录上传、非预期覆盖、把断线旧画面当作可输入现场。出现一次即修复并重测相关流程。
- **主观可用性**：每人完成任务后填写标准 SUS；均分 ≥75。单独询问清晰度与视觉信任感（1–5），两项中位数均 ≥4，记录理由，不以截图喜好替代任务结果。
- **真实回用**：上述 6 人进行 7 天试用；至少 4 人在至少 2 个不同日期自发使用 TinySSH 完成实际 SSH 工作。只计实际使用，不计“愿意使用”或被安排的回访演示。
- **机会不足**：试用期没有适用任务的参与者标为未观察到；先延长观察最多 7 天，仍不足则补充同标准参与者完成全套任务并单列批次，不能把没有任务视为回用成功。

本轮没有任何上述真人数据。门限在首位正式参与者开始前预登记；不能看到结果后调低。若主要痛点仍是布局/入口/状态理解，则回到相应阶段修复。可用性通过且回用不足时，发布候选保持待验证，分析替代成本和价值，不继续无限堆功能。

协作价值继续使用 [原 PV 计划](../validation-plan.md)，其参与者、任务及 gate 与这里分开。不要用客户端回用率替代 Agent 接管/交还的自发采用证据。

## 6. 验证命令与证据组织

### 6.1 基础命令

以仓库当前工具链为准，实施时把新增前端测试脚本登记到 `ui/package.json`。下面现有命令可以作为入口，但不代表已运行或全部足以验收：

```bash
# UI 编译（仓库根目录）
npm run build --prefix ui

# Rust 常规测试；实际网络/sshd 条件另按测试说明准备
cargo test --locked --workspace

# 开发服务器 / 原生客户端，按 README 和本机 Tauri 环境启动
npm run dev --prefix ui
cargo tauri dev
```

Rust 编译/测试顺序执行，避免同时争用构建锁影响性能测量。当前 `ui/package.json` 没有标准 test 脚本；R45 应把有价值的原散落验证脚本整合成可重复运行的测试入口，并删除写死个人浏览器路径的依赖。原生方式参照 [native-smoke README](../../scripts/native-smoke/README.md)，更新后不得依赖旧布局坐标。

### 6.2 每阶段证据包

建议目录 `docs/acceptance/ux-r1/<gate>/<date-commit>/`，仅在实际运行后创建结果，不预填 PASS。至少含：

- `report.md`：环境、commit、范围、通过/失败/环境阻塞、遗留项。
- `cases.csv`：用例 ID、条件、实际结果、证据路径、负责人、复测版本。

- `user-study/`：匿名原始任务记录、求助、SUS、实际回用日记；不提交密码/Token/私钥或生产输出。
