## 发现清单

### B1（阻塞）charset 线格式三方不一致：真实 app 保存主机必失败，demo 恰好掩住

**证据链**：

1. 真实后端 `Charset` 枚举 serde 为 `#[serde(rename_all = "lowercase")]`（`crates/session-api/src/lib.rs:367-373`，eaedbe5 引入）。`lowercase` 只做小写、**不插连字符**：序列化/反序列化变体名是 `"utf8"` / `"gbk"`。commit message「serde 小写持久化（vault hosts.charset 列同口径）」是误判——vault 列用的是 `'utf-8'`（带连字符，`crates/vault/src/lib.rs:66` 迁移 DEFAULT、`:281` `as_str()` 写入、`:337` `parse()` 读回），serde 线格式与 vault 列格式并不同口径。
2. UI 发送侧：`ui/src/App.tsx:2364-2367` 下拉 option 值为 `"utf-8"` / `"gbk"`，`:2268` state 默认 `"utf-8"`，`:2315` 每次保存（新建与编辑）都携带 `charset`。tauri 命令 `upsert_host(state, host: HostDraft)`（`src-tauri/src/main.rs:42-44`）直接 serde 反序列化——`HostDraft.charset` 的 `#[serde(default)]` 只兜「字段缺失」，不兜「未知变体值」。
3. UI 读取侧类型：`ui/src/App.tsx:36` `charset?: "utf-8" | "gbk"`，与真实 `list_hosts` 返回的 `"utf8"` 不符（GBK 主机返回 `"gbk"` 恰好撞对，UTF-8 主机返回 `"utf8"`）。
4. demo shim：`ui/src/demo.ts:44` 类型与 `:149/:155` `h.charset ?? "utf-8"` 全按 UI 口径接受——**与真实后端相悖**，正是 demo.ts 文件头三令五申要防的「shim 伪影误导走查」类别，这次方向反了：shim 放行了真实后端会拒绝的值。

**失败场景**：真实 Tauri app 中点「保存并连接」/「保存修改」任意主机（默认 UTF-8）→ `upsert_host` 反序列化报 `unknown variant 'utf-8', expected 'utf8' or 'gbk'` → 表单红字报错，**所有主机保存全部失败**（除非恰好选 GBK）。编辑已有 UTF-8 主机时另有一层：`editHost?.charset` 实为 `"utf8"`，select 无匹配项显示为空。验收文档 §5.33 的 GBK UI 验证全部走 demo 模式，Rust e2e（`gbk_charset_roundtrip_over_ssh`）在 Rust 侧构造 `HostDraft`，UI→tauri 的 serde 边界从未被真实 app 走查覆盖——这是验证缺口，非走查疏漏单点。

**修复建议**（二选一，并同步 demo）：

- **首选（Rust 一行）**：`#[serde(rename_all = "kebab-case")]` → 线格式变 `"utf-8"`/`"gbk"`，与 vault 列、UI 现值三方对齐（`Utf8` 的 kebab-case 恰为 `utf-8`）；如担心兼容可加 `#[serde(alias = "utf8")]`。
- 或 UI+demo 全改 `"utf8"`（vault 列格式本就独立，无需动）。
- 无论选哪个：demo.ts 的 charset 类型/默认值必须与最终线格式一致；修完后在**真实 app** 里补一次「新建主机保存→列表读回→编辑回填 select 显示正确」三步走查（§6.2 本就要求真实 app 硬性 gate）。

### H1（高）任务目标草稿/简报未按会话隔离：切会话竞态可把 A 会话目标带进（并可写入）B 会话

**证据**：`ui/src/App.tsx:441-442`（简报同步 effect）、`:445-453`（切会话 effect）、`:437-439`（refreshBrief 无过期丢弃）、`:486-506`（3s 轮询持续发 refreshBrief）。`goalDraft` 与 `brief` 都是全局单份 state，不带 sid 归属。

**两条失败路径**：

1. **切会话不清空旧草稿**：切会话 effect（`:445-453`）在目标会话无暂存时只复位 `goalDirty`，**不清 `goalDraft`**；而简报同步 effect 依赖 `[brief]`，brief 引用未变就不会重跑。切 A→B 后到 B 的简报返回之前（本地 IPC 一个 RTT，或最长一个 3s 轮询周期），「任务目标」框持续显示 **A 会话的目标文本**。用户若在此基础上开始编辑（goalDirty 置位，后续简报到达也不再覆盖），点保存即把 A 的目标（混着改动）写入 B——goal 是给 Agent 的委托指令，跨主机的错误委托会被 Agent 当真执行。
2. **过期简报回填**：A 会话的 `session_brief` invoke 在飞行中时切换到 B，A 的响应后到 → `setBrief(A 简报)` → 若此刻 goalDirty=false（B 无暂存），`:442` 直接 `setGoalDraft(A.goal)`，同样把 A 的目标显示到 B 并可保存落盘。（简报面板本身的同类串台是既有问题，goal 新增了写路径把显示问题升级成了数据污染。）

StrictMode 已核：切会话 effect 仅在 sid 变化时执行（StrictMode 只双跑 mount），暂存/恢复路径本身正确——本条不是 StrictMode 问题，是 sid 归属缺失。

**修复建议**：

```tsx
// ① refreshBrief 过期响应丢弃（顺带修复简报面板既有串台）：
const refreshBrief = useCallback(async (s: string) => {
  try {
    const b = await invoke<Brief>("session_brief", { sid: s });
    if (sidRef.current !== s) return;   // 过期简报丢弃
    setBrief(b);
  } catch { /* 会话已关 */ }
}, []);
// ② 切会话无暂存草稿时清空显示，等简报回填（改 :450 的 else 分支）：
else { goalDirty.current = false; setGoalDraft(""); }
```

## 正面评价

- goal 暂存按 sid 的设计目标（切签不丢草稿、保存即清暂存）实现干净，注释把「闭包取旧帧草稿」这一反直觉点讲透了。
- demo `set_session_goal` 对真实后端的镜像精度高（连审计 payload 字段名都对上了），说明作者确实对照过 `core-session` 实现而非凭空写。

- 死类清理彻底（删掉的旧 Timeline/brief-row 类零残留），tsc 干净。

## 结论

有条件通过。B1 是唯一阻塞项（一行 Rust 修复 + demo 对齐 + 真实 app 三步复验）；H1 建议同批修复（两行改动，顺带修好简报面板既有串台）。其余低危项可列后续轮次。B1 也暴露了流程缺口：**demo 模式验证不能作为「UI↔真实后端契约成立」的证据**——本仓库历史上三次被 shim 伪影误导都是 shim 少做了什么，这次是 shim 多接受了什么，两个方向都该在 §6.2 的真实 app gate 里覆盖_charset 这类 serde 边界值。
