## 1. 可以交给开发团队开工吗

**可以。** 当前文档已经能够指导团队分配负责人、制作可交互原型、冻结接口与失败语义、准备迁移/兼容样例、采集旧版基线。SSH 客户端优先、终端为主、文件按需打开的整体方向无需因本次审核退回重新定位。

“可以开工”有明确阶段边界：先执行 G0 的 R00–R04；产物实际完成并由 PM/UX、FE、Core、QA 共同评审后，再进入 G1 的正式重构实施。当前三张静态图、接口提案和本报告不能替代这个出口。后续 G1–G5 仍逐阶段验证，不能把独立文档审核解释为功能、性能、真人体验或发布验收通过。

在本次三路审阅范围内，**未发现尚未关闭的实质性 P1/P2 文档问题**。这表示已发现问题在设计层闭合，不保证未来实现和原型验证不会发现新的问题。

## 2. 独立审核如何组织

上一次交付只有作者自检。本次根据用户要求，另行组织三个独立 subagent，分别只读检查当前文档及其相关源码，先提交各自发现；主代理修订文档后，由原评审者重新阅读并判定关闭情况。技术和交付复审又发现两处 P2，修订后再次做针对性复核。

| 审阅者 | 主要范围 | 审核轮次与最终结论 |
|---|---|---|
| `/root/ux_independent_review` | 产品定位、终端优先结构、连接/焦点/文件/协作交互、三张视觉图、窄窗与分屏 | 初审 → 修订复审；2 项 P2 关闭，1 项布局细化补齐；可启动 G0 |
| `/root/contracts_independent_review` | Rust/SessionApi/MCP 兼容、传输提交与取消、控制权、模式语义、停用生命周期 | 初审 → 修订复审 → shim 边界针对性复核；3 项 P1、2 项 P2 关闭；可启动 G0 |
| `/root/delivery_independent_review` | 任务依赖、验收可执行性、用户试验、性能口径、跨文档治理 | 初审 → 修订复审 → 历史阈值与导航复核；5 项 P2 关闭，导航勘误完成；可启动 G0 |

这里的“独立”指不同 subagent 分别形成审阅意见，并非外部第三方或真人团队签署。三位评审者未修改产品或文档，修订由主代理完成。此次没有启动应用、执行产品测试或招募真人用户。

## 4. 开工范围与 G0 出口

| 现在可以开展 | 进入 G1 前必须具备的实际证据 |
|---|---|
| R00 范围核对和任务分配 | 现有功能去向、首版限制、行为变更清单、实际负责人 |
| R01/R02 原型和组件制作 | 可交互原型走完五条主要任务；覆盖 S01–S11 的关键失败、窄窗、键盘及明暗状态；组件与对比度记录 |
| R03 接口和兼容设计、隔离技术探针 | C1–C10 正式 wire/错误码/状态转移；提交未知、模式拒绝、admission、连接取消竞态的可断言序列 |
| 迁移/协议样例准备 | 脱敏 fixture 清单、旧 Agent 配置及旧客户端模式错误路径的预期；实现可以依阶段完成，预期先冻结 |
| R04 原生基线采集 | 固定环境、原始旧版样本、采样脚本、统计口径与限制；不能使用历史报告替代本轮数据 |

G0 评审记录必须包含版本或文件摘要、日期、PM/UX、FE、Core、QA 的实际评审人、结论和遗留。未分配人、缺证据或关键语义未关闭时，G0 保持待执行/阻塞。任务表目前只有角色，没有代替开发团队指定个人、承诺工期或伪造签署。
