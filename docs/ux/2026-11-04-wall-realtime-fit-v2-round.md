# tmux 监控大屏：300ms 节拍 + 宽高双约束适配 v2（2026-11-04）

用户对上轮修复的复验反馈：「2s 刷新是硬伤，最好不要这样。tmux 子窗口分辨率布局似乎还是没有自适应好。」

## 一、诊断

### 2s 刷新硬伤

抓取每周期本就只是一条批量 exec（`tmux_wall_cmd` 一次抓全部目标，capture-pane 是服务端内存读，亚秒节拍对远端无感）——2s 纯粹是前端保守节拍。键入侧更糟：`tmux_wall_input` 补拍帧只含回显，命令输出（`ls` 的结果）在其后百毫秒才产出，旧节拍下用户敲完命令要等 2s+ 才看到输出，观感即「输入有问题」的另一半。

### 自适应没做好（v1 的两个盲区）

v1 只按宽缩放且网格封顶 1：大格子（2×2/solo）scale=1 时 64 行快照超出格子高度，**当前屏底部仍被裁**（上轮只救了 4×4 小格）；不放大=右侧留白，观感就是「没自适应」。根子是协议里没有「当前屏行数」——快照恒 64 行（`-S -40`），前端不知道末尾几行是当前屏，没法做「当前屏完整」约束。

## 二、修复

1. **协议加 pane 高度**（core-session + session-api）：`@@WALL|i|n|rows` 三段帧头，循环体顺带 `display-message -p -t "$t:" '#{pane_height}'`（pane 类尾冒号坑 81 同族）；失败/非数字落 0=前端退化按宽缩放，绝不拖累本格快照。`tmux_wall_input_cmd` 补拍段同款。`TmuxWallCell.rows: u32`（serde default）。
2. **节拍 2s→300ms**（tmux-wall.tsx）：在飞守卫（找茬四轮 A1）在亚秒节拍下天然成为 RTT 自适应——拍未回则跳过，链路慢时自动降频「回一拍拍一拍」，绝不叠发。stale 阈值 3→10 拍（10×300ms=3s，与旧 3×2s 同为秒级，太短闪误报）。
3. **键入后主动补拍**：sendNow 链成功后 150ms 触发 `tickRef.current?.()`（给远端 shell 产出输出的窗口），输出尽快显形不等节拍；在飞守卫防叠。
4. **宽高双约束 applyFit v2**：`scale = min(格宽预算/当前屏自然宽, 格高预算/当前屏行数×行高, 2.5)`，下限 0.25——当前屏永远完整可见（硬约束），历史裁切优先级最低（底部锚定裁顶部）；横向按**当前屏**最宽行铺满（cellCols 改末尾 rows 行语义——历史超宽行不再把整格字号拉小）；cap 统一 2.5 只防极端窄快照荒诞放大，邻格字号一致让位于「每格铺满」。行高探针 lineHRef（computed lineHeight，CSS 钉 1.25）。

## 四、教训

1. **性能语义要先问「约束在哪」再定节拍**：批量 exec+内存读命令的节拍可以激进，在飞守卫就是自适应阀——「保守间隔」不该替代「并发上限」。
2. **监控语义的适配目标是「当前屏完整」不是「全部内容可见」**：需要协议把「哪段是当前屏」告诉前端（pane_height），否则缩放永远在猜。
